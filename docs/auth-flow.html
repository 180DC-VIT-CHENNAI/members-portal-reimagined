1 · Account onboarding

Anyone can request an account. A board member (power ≥ 100) approves it. Approval creates the users row, a long-lived admin_tokens row, and emails the token to the member's inbox — possession of the inbox is the proof of identity (magic-link model).

    A->>D: INSERT audit_log (signup_approved)

One active token per email. Every issuance path (admin-tokens, board-users, advisory-members, signup approval, rotate) first DELETEs the prior row — admin_tokens.email is UNIQUE.

2 · Google sign-in (Clerk)

Two different tokens exist and should not be confused:

  • Clerk JWT (~60 s) — minted by Google/Clerk; proves “you own this Google account”. Rendered client-side by getToken().
  • Admin Bearer token — long-lived (no server expiry); the credential that unlocks the portal API.

After the security fix, clerk-login never trusts a client-supplied email. It resolves the account via Clerk's Backend API and only accepts Clerk-verified email addresses.

3 · Token login

The portal's “Continue with Token” button posts to /api/auth/token-login — production-safe. The legacy /api/dev-login route is development-only (403 when ENVIRONMENT=production).

sequenceDiagram
    autonumber
    actor U as Member
    participant F as Frontend SPA
    participant A as Admin API (Worker)
    participant D as D1 (180dc-db)

    U->>F: Paste token from email
    F->>A: POST /api/auth/token-login {token}

    A->>D: SELECT admin_tokens WHERE token = ?
    Note over A: missing / revoked / expired → 401
    alt users row missing
        A->>D: INSERT users from token payload
    end
    A-->>F: 200 {email, name, role, powerLevel}

Forgot your token? POST /api/auth/forgot-token (rate-limited 3/hr) re-emails the existing token to the registered inbox and always returns the same success message to prevent email enumeration.

    U->>A: POST /api/auth/rotate-token (Bearer, 3/hr)

    %% link
    U->>A: POST /api/auth/link-clerk {clerkToken} (Bearer)
    A->>A: verifyToken(JWT) → sub
    Note over A: client-supplied clerkUserId is NOT accepted
    A->>D: another user already holds this sub? → 409
    A->>D: UPDATE users SET clerk_user_id=sub, oauth_enabled=1
    A-->>U: 200 "Google login enabled"

    %% unlink
    U->>A: POST /api/auth/unlink-clerk (Bearer)
    A->>D: UPDATE users SET clerk_user_id=NULL, oauth_enabled=0
    A-->>U: 200 "Google login disabled"

Security notes & the fixed exploit

The vulnerability (fixed): POST /api/auth/clerk-login previously auto-linked by a client-supplied email in the request body. A valid Clerk JWT (60 s) + any member's email returned that member's long-lived admin token — a power-10 friend could log in as a power-100 board member without ever touching their inbox.
The fix (deployed in apps/admin-api/index.ts):
  1. Email is resolved from Clerk's Backend API only; client email is ignored unless it is a Clerk-verified address.
  2. Stored clerk_user_id links that don't match a verified email are ignored (kills already-taken-over accounts).
  3. One Clerk user ID ↔ at most one member (409 + unique partial index idx_users_clerk_user_id).
  4. link-clerk now requires a verified clerkToken JWT; client-supplied clerkUserId was removed.
  5. Audit entry (clerk_linked) is written on every new link.

Reminders

  • Admin tokens never expire server-side; they are only killed by rotation or revocation. Compromised token → rotate immediately.
  • After a takeover incident: rotate the token, unlink/re-link Google, and inspect audit_log (clerk_linked) to identify the attacker's Clerk ID.
  • If ENVIRONMENT is unset on the deployed worker, dev-login opens and a chairperson token for admin@vitstudent.ac.in gets seeded on every run — verify the var is production in the dashboard.
  • Token login runs through the production-safe /api/auth/token-login; dev-login stays dev-only. Both are rate-limited per IP.
