# ADR-007: Rewrite the members portal on Void, with Google-only sign-in and a personnel system

- **Status:** implemented. Since the cutover (PR #37, 2026-10-18) the portal serves `180dc.vitcc.org`; the old `apps/admin-api` + `apps/frontend` Worker stays deployed without a domain for rollback until its retirement is approved.
- **Date:** 2026-10-16

## Context

The current backend is a single 12k-line `apps/admin-api/index.ts`. Its schema is built at runtime (`ensureTables`/`runMigrations`), and access comes from registry tokens plus coarse `power_level` thresholds. The club needs the following:

- **Sign-in:** members sign in with Google only, with no tokens.
- **Personnel:** a real personnel system with a lifecycle, titles kept separate from access, terms and tenure history, granular permissions, rich profiles, a directory, and bulk CSV.
- **Codebase:** a codebase that is easy for both people and agents to navigate.

The portal is a separate, blank-data deployment. The user explicitly chose not to migrate records or R2 objects from the old Worker.

## Decision

- Build a new app in `apps/portal` on [Void](https://void.cloud) (Vite plugin, Cloudflare Workers) in **SPA + API** mode:
  - Static assets are served from the edge without a Worker request.
  - Only `/api/*` runs the Worker.
- Use file-based routes in `routes/api/**` and server code in `src/server/`. Resolve authentication and permissions in route guards rather than global middleware: global middleware would make static assets invoke the Worker.
- **Database:** D1 through Drizzle (`db/schema/*`). Migrations live in `db/migrations/` (generated by `void db generate`) and are applied by Void on deploy. Reference data is seeded in migrations with `INSERT OR IGNORE`.
- **Auth:** Better Auth through `void/auth`, with the Google provider only and email/password disabled. Database hooks in `auth.ts`:
  - create an account only for a verified email that matches an invited, active or on-leave person;
  - activate an invited person on their first sign-in;
  - refuse sessions for people without access.
- **Access:**
  - A typed permission catalogue in `src/server/permissions.ts`.
  - Access roles (`access_roles` and `role_permissions`, each grant with scope `global` or `department`) plus per-person grants (`person_grants`, optionally limited to one department).
  - Positions (titles) never grant access.
- **Per-request check:** protected API handlers resolve the session to a `people` row with status `active` or `on_leave` through `src/server/guard.ts` and `src/server/principal.ts`. Changing someone's status therefore ends their access on their next request, and their sessions are also deleted.
- **Rollout:** the new app deploys to its own Worker (`180dc-portal`). A final cutover PR moves `180dc.vitcc.org` to it and retires `apps/admin-api` and `apps/frontend`. Every existing feature is ported before that cutover.

## Alternatives considered

- **Incremental (strangler) migration inside `admin-api`:** keeps the runtime schema and the monolith, and mixes two auth models for a long time.
- **Keeping the Worker's own Google OAuth (PR #13):** works, but duplicates what Better Auth provides (PKCE, sessions, account linking, rate limits).
- **Server-rendered pages:** every page view would count as a Worker request.

## Consequences

- **Positive:**
  - Typed schema and routes, one file per URL, generated migrations and fast builds (about 3 s).
  - Permissions can be extended by adding a key and granting it in a migration.
- **Negative:**
  - Two apps exist side by side until the cutover.
  - Every feature has to be ported.
- **Risks:**
  - Void is new (1.x). Pin the version, and keep `void.lock.json` committed once the first deploy creates it.

## Compatibility impact

None until the cutover. At cutover the old token API (`admin_tokens`, `/api/auth/*` custom routes) is retired. Members re-enter only through Google sign-in with an invited email.

## Migration impact

Reference data is seeded by migrations: departments, roles, positions, the current term, and the first admin `srijan.guchhait@gmail.com` (admin role, title "Technical Lead - DevOps & Cloud"). Other members are added through invitations or bulk CSV import. Databases and R2 buckets otherwise start empty. There is no old-to-new data or object migration in this rollout; existing data remains in the old deployment.

## Conditions for reconsideration

Reconsider if Void stops supporting direct Cloudflare deploys, if Better Auth cannot meet a sign-in requirement, or if D1 limits are reached.
