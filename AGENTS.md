This file is the primary entry point for any coding agent working on the `180dc-admin-website` repository.

On this branch, edit only that file, follow `CONTRIBUTING.md` for writing rules, and open PRs into `reimagined`. Do not make code changes here: code work branches from and targets `main`. ## Project classification

- **Project mode:** BROWNFIELD
- **Reason:** A meaningful, deployed implementation already exists. The `admin-api` Worker and the Vite/React frontend are in production use. The `public-api` and `job-processor` Workers, plus several aspirational architecture documents, are placeholders or historical targets.
- **Branch context:** This documentation was produced against the `main` branch. Some unmerged feature work exists on `dev` and other branches, but agents should treat `main` as the production source of truth unless explicitly told otherwise.

## What this repository is

The 180 Degrees Consulting VIT Chennai platform:

- Public landing website (`apps/frontend`) — Vite + React SPA deployed to Cloudflare Pages.
- Members portal (`/members`) — authenticated admin dashboard for members, directors, and board members.
- Admin API (`apps/admin-api`) — single Hono Worker on Cloudflare Workers that serves the frontend, handles public API calls, and runs the member-facing backend.
- Public API (`apps/public-api`) — placeholder Worker. Not used in production today.
- Job processor (`apps/job-processor`) — placeholder Queue consumer Worker. Not used in production today.
- Shared `packages/db` — currently a placeholder. The real schema lives inside `apps/admin-api/index.ts`.

## Mandatory engineering rules

1. **Do not treat `packages/db/schema.sql` as authoritative.** It contains destructive `DROP TABLE` statements and does not reflect the runtime schema. The canonical schema and migrations live in `apps/admin-api/index.ts` (`ensureTables` and `runMigrations`).
2. **Do not run `packages/db/schema.sql` against any D1 database.** It will destroy data.
3. **Do not edit generated or placeholder files directly:**
   - `apps/admin-api/worker-configuration.d.ts` is generated by `wrangler types`.
   - `apps/public-api/index.ts` and `apps/job-processor/index.ts` are placeholders.
4. **All schema changes must be backward-compatible and idempotent.** Add new columns/tables with `IF NOT EXISTS` or `ALTER TABLE ... ADD COLUMN` wrapped in `try/catch`. The production database has live data.
5. **Auth is custom token-based, not Clerk, for the members portal.** The frontend uses Clerk for Google OAuth, but the backend validates a `Bearer` token against the `admin_tokens` table.
6. **Do not expose secrets in documentation, logs, or code.** Environment variables and Wrangler bindings must be referenced by name only.
7. **Rate limits and email quotas are enforced in D1.** Respect the `rate_limits` table, and the SMTP hourly cap in `email_hour_count` (500 messages/hour; the queue uses at most 90%). Spacemail SMTP is the only email provider — Resend was removed; do not reintroduce a second provider without a decision.
8. **Meet links are hidden 24 hours after the scheduled time.** This is implemented in the SQL that returns meet records.
9. **The `QUEUE` binding in `admin-api` is configured but not actually used.** Bulk email (newsletters, events, meet notifications) is enqueued in the `email_queue` table and drained by the `* * * * *` cron trigger with adaptive pacing (up to 15 messages/minute, ≤500/hour); every campaign is one message per recipient, 1.5 s apart (newsletter and event mail personalized per subscriber); no campaign uses BCC batches. `pending_emails` is legacy and still drainable via `POST /api/meets/process-queue`. The `job-processor` consumer is a placeholder.
10. **Frontend API calls are proxied through the Cloudflare Pages `_middleware.ts` to `admin-api.technical-vitc.workers.dev`.** Do not assume the worker is reached at `180dcvitc.org/api/*` from the Pages site, even though the worker route pattern says that.

## Git workflow: pull requests and releases

Remotes:

- `origin` = `https://github.com/180DC-VIT-CHENNAI/members-portal-reimagined` (development repository)
- `upstream` = `https://github.com/180DC-VIT-CHENNAI/180dc-admin-website` (production repository)
- Branch `upstream-main` on `origin` is a read-only mirror of `upstream` `main`, force-synced hourly by `.github/workflows/sync-upstream-main.yml`. Use it to compare or cherry-pick; never commit to it.

Rules:

1. **Every change goes through a pull request.** Never push directly to `main` (or any default/protected branch) on either remote. Work on a feature branch and open a PR.
2. **PRs target `origin` `main`.** All feature, fix, and docs PRs are opened against `main` on `origin` (`members-portal-reimagined`). Do not open feature PRs against `upstream`. The only exception: junior consultants editing `180DC_Unified_Platform_Problem_Statement.md` open their PRs against the `reimagined` branch, which is reserved for that document and receives no code work.
3. **Release on `origin` before promoting.** Once the work on `origin` is complete and tested, cut a versioned release on `origin` (a semver git tag such as `v1.4.0` plus a GitHub release with notes).
4. **Only versioned releases go to `upstream`.** After the release is published on `origin`, open a single PR from that release to `upstream` (`180dc-admin-website`). The PR title must include the version (e.g. `Release v1.4.0`) and the body must link the `origin` release and summarize its changes.
5. **Never open a PR to `upstream` with untested or unreleased work.** If something is not yet in a tagged `origin` release, it does not go upstream.

## Repository boundaries

- `apps/admin-api/index.ts` is the canonical backend. Any new API route, schema change, or business rule belongs there unless you are explicitly building a new service.
- **Newsletter data lives in a separate D1 database**, bound as `NEWSLETTER_DB` (`newsletter-db`). It holds `newsletters`, `newsletter_subscribers`, `newsletter_authorized_emails`, `newsletter_otp_codes`, and `newsletter_sessions`. All newsletter routes must use `newsletterDb(c)`, not `c.env.DB`; `ensureNewsletterReady(c)` (invoked by middleware) creates the tables. The old copies in `180dc-db` are legacy backups — do not write to them.
- `apps/frontend/` is the public site and members portal. It is a Vite React SPA.
- `packages/db/` is currently a placeholder. Do not add production SQL migrations there without also updating `admin-api/index.ts`.
- `docs/architecture/` contains both current decisions and historical/aspirational documents (ADR index under `docs/architecture/decisions/`). Read `docs/architecture/backend-architecture-cloudflare.txt` with care: it describes a Cloudflare Access + Next.js design that was not implemented.
- `docs/design/DESIGN.md` and `docs/design/plan.md` are the source of truth for visual design.
- `docs/product/REPORT.md` is a plain-English feature inventory and is useful for product context.
- `docs/operations/NEWSLETTER_EDITOR.md`, `SPACEMAIL_SETUP.md`, and `SES_SETUP.md` are operational docs for the newsletter/email subsystem.

## Commands to use

Install dependencies:

```bash
pnpm install
```

Build the frontend:

```bash
pnpm turbo run build
# or
pnpm --filter frontend run build
```

Verify the admin-api compiles and bundles with Wrangler (no `tsconfig.json` is present):

```bash
cd apps/admin-api
pnpm wrangler deploy --dry-run
```

Run a worker locally:

```bash
cd apps/admin-api
pnpm wrangler dev

# In another terminal
cd apps/frontend
pnpm dev
```

Deploy a worker:

```bash
cd apps/admin-api
pnpm wrangler deploy
```

Deploy the frontend to Cloudflare Pages:

```bash
cd apps/frontend
pnpm run build
pnpm wrangler pages deploy dist --project-name 180dc-admin-frontend
```

Root `package.json` scripts:

```bash
pnpm run build              # builds frontend only
pnpm run build:frontend     # builds frontend only
pnpm run deploy:backend     # deploys admin-api
pnpm run deploy:frontend    # builds and deploys frontend
pnpm run deploy:all         # deploys backend then frontend
pnpm run generate:completed-projects  # runs scripts/generate-completed-projects.mjs
```

## How work must be verified

1. Run `pnpm install` if dependencies changed.
2. Run `pnpm turbo run build`.
3. For admin-api, run `pnpm tsc --noEmit` inside `apps/admin-api`.
4. Run `pnpm test`, the admin-api end-to-end suite. It starts the worker on an empty local D1, so it also checks that `ensureDbReady` creates the schema and `runMigrations` run cleanly.
5. For changed endpoints without a test yet, add one under `tests/api/`.
6. For frontend changes, run `pnpm --filter frontend run build`.

Run the end-to-end API suite after every backend change: `pnpm test` (emails are captured, none sent), or `TEST_EMAIL=you@example.com pnpm test:mail` to also receive one of each email. Every new or changed route needs a test in `tests/api/` (see `tests/README.md`). A test that exposes a bug you are not fixing goes in `tests/lib/known-issues.mjs` as a `todo`. There are no frontend tests yet.

## Important hazards for agents

- **Schema drift:** The `packages/db/schema.sql` file does not match the tables the Worker creates at runtime. Always use `apps/admin-api/index.ts` as the schema source of truth.
- **Recruitment feature was removed.** `runMigrations` drops recruitment tables. Do not reintroduce them without an explicit decision.
- **Dual project tables:** `projects` is the global project table with tasks/roles/departments. `department_projects` is a separate per-department project tracker. Do not confuse them.
- **Power level vs role name:** Many route checks use `power_level` thresholds (`>= 100`, `>= 50`, `>= 10`) not role IDs. Some comments say "Lead" but the threshold is 50 (director). Trust the code.
- **Email daily cap:** The backend enforces a hard cap of 100 emails per day via `daily_email_count`.
- **Meet link visibility:** The SQL queries for listing meets return `NULL` for `meet_link` when `julianday(scheduled_at) < julianday('now', '-1 day')`. Do not change this behavior unless a product decision is recorded.
- **Advisory members:** `role_id = 'advisory'` have `power_level = 30`. They cannot access team instances and are excluded from some recipient lists.
- **CSP and security headers are hardcoded in `apps/frontend/functions/_middleware.ts`.** Any new external domain (e.g., new analytics, fonts, auth provider) must be added there.
- **Public API and job processor are placeholders.** Do not implement production features in them without an explicit plan.
